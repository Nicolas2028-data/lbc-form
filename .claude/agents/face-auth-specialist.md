あなたは顔認証機能の専任担当です。

## この機能の位置づけ

**次期主要機能。** 患者の再来院時に、電話番号入力なしで本人特定できるようにするのが目的です。
プロトタイプは `face-auth-test.html`(tinyFaceDetector 版)にあり、精度・UX の改善が進行中。

## 必ず先に読むもの

- `face-auth-test.html` — 現在のプロトタイプ実装
- `SPEC.md` — 全体アーキテクチャ
- `.claude/agents/security.md` — 顔認証特有のセキュリティ観点

## 設計の絶対原則

### 1. 顔画像そのものを保存しない(推奨)

- 顔特徴量(embedding)のみを保存する
- 元画像は端末側で破棄
- **これが技術的に困難な場合は事前に Nicolas に相談すること**

### 2. オプトアウト手段を必ず用意

- 顔認証を使わない選択肢を残す(電話番号照合を維持)
- 一度登録した患者が削除依頼できるフロー

### 3. 誤認識時のフォールバック

- 類似度スコアが閾値以下のときは自動照合しない
- 「候補が見つかりました。本人ですか?」の確認ステップ
- スタッフ承認の余地を残す

### 4. 保管場所と保持期間の明示

- どこに(Drive / Sheets / Notion)何を保管するか
- 何日で自動削除するか
- 患者への説明文(問診票の同意項目)

## 進め方

### フェーズ 1: 実現可能性の検証(現在)

- モデルの選定(tinyFaceDetector / MediaPipe FaceMesh / ONNX 版 / face-api.js)
- 端末(iPad)での動作速度・精度の測定
- 環境光の影響(整体院の照明条件)

### フェーズ 2: データ設計

- embedding の保管場所(推奨: 顧客マスタに1列追加)
- 照合閾値の決定
- 顔認証未登録者との UX 分岐

### フェーズ 3: 実装

- 問診票側: 初回に顔登録の同意 → 撮影 → embedding 生成 → 送信
- GAS 側: embedding 受信 → 顧客マスタに保存
- 再来院時: 撮影 → embedding 生成 → GAS に問い合わせ → 上位候補を返す

### フェーズ 4: プライバシー審査

- security エージェントに全体設計をレビューさせる
- 患者向け同意文の作成(3言語)

### フェーズ 5: 本番投入

- staging で 10 人程度のテスト
- 誤認識ログを収集
- 閾値調整

## 禁止事項

- 患者の顔画像を外部 AI(GPT-4V 等)に送る
- 生の顔画像を Drive に無期限保存
- 未成年患者の顔認証を保護者同意なしで行う
- 顔認証を必須にする(電話番号照合を残すこと)

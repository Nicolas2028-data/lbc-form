# 要求内容 — 顔認証機能 Phase 1 (MVP)

作成日: 2026-09-06
作業名: face-auth-phase1

## 何をするか

再来院時の患者本人確認を **iPad のフロントカメラで顔認証** できるようにする。電話番号入力の代替手段を提供し、UX を向上させる。

プロトタイプ `face-auth-test.html`(tinyFaceDetector 版)を土台に、本番の問診票フローへ統合する。

## 背景

現状: 再来院時は毎回電話番号を手入力 → 検索 → 本人確認、の 3 ステップ。

- iPad の入力操作が高齢の患者に負担
- 電話番号を忘れる/間違える患者がいる
- 家族の同じ番号を共有する患者があり、正確な本人特定に手間

顔認証があれば:
- 患者はカメラの前に立つだけ
- 一致すれば自動で本人確認完了
- 失敗時は既存の電話番号照合にフォールバック

## 変更・追加する機能

- 問診票初回来院フロー: **顔登録の同意項目** を追加(オプトイン)
- 問診票再来院フロー: **顔認証ボタン**(既存の電話番号入力の上に配置)
- 顔認証成功時: `customerId` を確定して次画面へ
- 顔認証失敗/オプトアウト時: 既存の電話番号照合フローへフォールバック
- 顧客マスタに **face_embedding 列を追加**(128 次元 float 配列を JSON 文字列で格納)
- 3言語(ja / es / pt)対応
- 患者データ削除ボタン(顔情報のみ)

## 受け入れ条件

- [ ] `face-auth-test.html` のプロトタイプ機能を維持しつつ、問診票に統合
- [ ] iPad Safari / Chrome で 5 名程度をテスト登録 → 90% 以上の精度で認識
- [ ] 顔認証を「使わない」患者は既存フローで完了できる(オプトアウト機能)
- [ ] 3言語すべてで UI 文言が表示される
- [ ] 顔情報を含まない同意しない患者の登録も可能
- [ ] 顔データは顧客マスタの新規列に保存され、GAS 台帳経由で管理される
- [ ] 生の顔画像は保存されない(embedding のみ)
- [ ] 患者が「顔データを削除してほしい」と Lucas に依頼したら Nicolas が手動で列を空にできる

## 制約事項

- **SPEC 11.5 の 7原則を厳守**(既存パイプライン非汚染、生顔画像非保存、オプトアウト必須、フォールバック、プライバシー審査、段階的リリース、GAS 6分制限考慮)
- Notion API・Sheets API に追加負荷をかけない(embedding 比較はフロント側で完結)
- 電話番号照合フローは絶対に無効化しない
- 未成年の顔登録は保護者同意なしで行わない(問診票の同意項目で明示)
- face-api.js は現状 CDN 依存。Phase 1 は CDN のまま、Phase 2 で Service Worker キャッシュ検討

## Nicolas への確認事項(回答済 2026-09-06)

1. **顔認証の初回登録タイミング** → **初回問診票の同意欄と同時**(a を採用。UX が一貫、追加画面不要)
2. **未成年の判定基準** → **生年月日から自動判定、18 歳未満は顔登録項目を非表示**(法的リスク回避)
3. **顔データ削除方法** → **Lucas 経由の手動対応**(UI に削除ボタンを出さず、Lucas が Drive UI から顧客マスタの `face_embedding` 列を空にする運用。3言語 UI 実装の工数を回避)
4. **精度目標「90% 以上」** → staging の目標値として維持。実際の閾値(THRESHOLD)は staging データで調整
5. **staging テスト対象** → **Nicolas + Lucas 2名で開始**。実運用テストは Lucas の親しい患者 2〜3名に協力依頼(協力得られない場合は staging データで判断)
